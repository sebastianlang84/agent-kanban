# agent-kanban

A shared SQLite ticket board for AI coding-agent sessions, accessed through a Python CLI.

> **Agent-maintained.** All code, documentation, commits and pushes in this repository come from AI coding agents
> (Claude Code and Codex). I contribute ideas, set the direction and review the output; I don't write code, commit or push.

## Why it exists

Agents working in separate sessions or worktrees need to know who owns a task, what changed,
and what remains. A chat message alone is easy to lose when a session ends or another agent
starts. agent-kanban records claims, progress, handoffs, requests, and decisions in one board.

## How it works

`kb` is a Python standard-library program; `kb.py` is a compatibility symlink to it. The board
lives in a local SQLite database on one host. Transactions and guarded updates enforce ticket
ownership. Guest machines use the same commands over SSH, without an application server.

Tasks move through `todo`, `doing`, `blocked`, `done`, and `abandoned`. Requests carry an
addressee and a recorded reply. Session tokens identify scripts; hooks discover supported
harness identities and record start, stop, and end events. Hooks show a session new requests
at its next prompt; a new session also sees open requests to its name that an earlier session
left unanswered. The shipped
[using-kb skill](skills/using-kb/SKILL.md) explains the workflow to agents.

## Requirements

- Python 3.9 or newer, with SQLite support. Runtime dependencies are in the standard library.
- A local filesystem for the host database; SSH client/server access for guests.
- Git for repository/worktree detection and the development tests.
- Linux is the primary host environment. Windows is supported as an SSH guest.

## Install and quickstart

From this checkout, inspect setup and install the host:

```sh
./install.sh --host --dry-run
./install.sh --host
export PATH="$HOME/.local/bin:$PATH"
```

Setup creates `~/.config/agent-kanban/config`, links `kb` into `~/.local/bin`, installs the
skill, and merges hooks into existing Claude Code, Codex, and pi configuration directories.
It backs up changed configuration files and reports entries requiring manual correction.
Setup skips harness directories that do not exist. Review its output; Codex hooks may need
trust confirmation, and pi may need `+extensions/kb.ts` in its extension settings.
On Windows, use `py -3 .\kb setup --guest <ssh-destination>`.

For a plain terminal or script, start a token session and complete a task:

```sh
session=$(kb start --as demo)
kb --session "$session" add "Document the example project" --repo example-project --claim
kb --session "$session" board --repo example-project
# Substitute the ticket ID printed by add:
kb --session "$session" note <id> "Documentation is ready for review."
kb --session "$session" close <id> --where "local checkout" \
  --changed "Added usage examples" --open "Nothing"
kb --session "$session" end
```

Inside a supported agent harness, identity is automatic and newly added tasks claim by default.
Run `kb --help` for commands and `kb <command> --help` for options. You can also run
`python3 ./kb` directly without installing it.

## Configuration

Settings use `KEY=value` lines in `$XDG_CONFIG_HOME/agent-kanban/config`, defaulting to
`~/.config/agent-kanban/config`. Environment values generally override that file.

| Setting | Purpose and default |
| --- | --- |
| `KB_DB` | Database path; `~/.local/share/agent-kanban/board.sqlite`. |
| `KB_HOST` | Guest SSH destination; empty selects a local board. |
| `KB_INSTALLATION` | Installation ID generated by setup. |
| `KB_SSH_KEY` | Dedicated guest key generated by setup. |
| `KB_CLIENT` | Optional client label for host-side service calls. |
| `KB_CLIENT_NAMES` | Display aliases, such as `desktop-2026:desktop,laptop-2026:laptop`. |
| `KB_RELEASE_DAYS` | Release idle `doing` claims after 7 days; 0 disables. |
| `KB_RELEASE_BLOCKED_DAYS` | Release idle `blocked` claims after 30 days; 0 disables. |
| `KB_COORDINATOR` | Host session permitted evidence-based request completion; `coordinator`. |
| `KB_ORCHESTRATOR` | Optional approval delegate; read from the host config file only. |

Keep the database outside Git working trees, or in an explicitly ignored path. Store no secrets
in titles or notes that you may export. Start hooks apply idle-release rules; a note or `kb touch`
keeps ticket activity current. Curator-held claims and recovery are exempt.
Set `KB=0` to disable hooks for automated runs. The compatibility switch
`BRAIN_SESSION_CONTEXT=0` also disables hooks. `KB_SESSION` and the `--session` option select a
saved token identity; do not put tokens in a repository.

## Guests and SSH

On a guest, run `./install.sh --guest <ssh-destination>`. SSH must work without an interactive
prompt and the host key must already be trusted. Setup creates a dedicated key and prints a
`kb authorize` command for the human curator to run on the host.

Authorization installs a restricted SSH forced command tied to the guest installation ID.
Guest commands then work like local commands. Hooks use short deadlines and spool lifecycle
events while offline; ordinary commands report an unreachable host. A guest cannot act as the
host curator. See [host and guest architecture](https://sebastianlang84.github.io/agent-kanban/host-guests.html) and the
[workflow](docs/workflow.md) for protocol, identity, and offline behavior.

## Backup and compatibility

Use `kb backup --help` for snapshots and rotation. `kb restore <backup>` is a host-curator action
that places restored claims into recovery until reconciled. Keep an independent backup before
upgrading an existing board.

The CLI migrates older versioned schemas and imports the earlier unversioned board on first
open. [legacy/](legacy/README_a.md) retains the old CLI only to build migration-test inputs.
It is not the executable to install for a new board.

## Optional helpers

The scripts in [tools/](tools/) support local automation; setup does not install or launch them.

- `kb-watch` streams new notes for a session, with optional `--exec` handling. It finds the
  database as `kb` does (`KB_DB` from the environment or the config file, else the default path)
  and stores its cursor beside it. Linux inotify wakes it on writes; other environments fall back
  to polling. It runs on the host only; a guest runs it there over ssh.
- `autopilot` routes stalled work into requests. Preview with `tools/autopilot --dry-run`.

## Status and limitations

Version 0.4.0. The project includes migrations, race tests, host/guest tests, restore tests, and
harness-hook tests. It is a small shared board for trusted agents and an operator, with several
limits:

- Advisory session names are routing labels, not authentication. One trusted human curator is
  assumed on the host; the board is not a multi-tenant security boundary.
- There are no task dependency graphs, built-in web server, or hosted synchronization service.
- Idle expiry can release work a live session still intends to resume. Inspect prior handoff
  information before claiming automatically released work.
- Harness integration depends on each harness's hook support and configuration.
- Optional automation requires local configuration and supervision.

## Development

Use a separate worktree if an installed `kb` points into your checkout. For manual checks, set
`KB_DB` to a temporary file outside the repository. Install the pinned test dependencies in a venv:

```sh
python3 -m venv .venv
.venv/bin/pip install -r requirements-ci.txt
.venv/bin/python -m pytest tests -q -p no:cacheprovider -n 8 -k 'not timing'
.venv/bin/python -m pytest tests -q -p no:cacheprovider -k timing
```

Timing checks run separately so parallel load does not affect their budgets. The standard-library
runner is also available: `python3 -m unittest discover -s tests`. Release tags use `vX.Y.Z`;
`python3 ci/check_release.py vX.Y.Z` checks version consistency and release metadata.

Read the [workflow](docs/workflow.md), [architecture decisions](docs/adr/),
[ticket lifecycle](https://sebastianlang84.github.io/agent-kanban/ticket-states.html), and [request sequence](https://sebastianlang84.github.io/agent-kanban/request-sequence.html).
